### Правило: все правила проекта — в AGENTS.md (КРИТИЧНО)

- Все правила кодирования, архитектурные ограничения, дисциплина вызова инструментов
  и Blazor-паттерны находятся **исключительно в этом файле** (`AGENTS.md`).
- `MEMORY.md` содержит кросс-сессионные знания (архитектурные решения, контекст проекта,
  обнаруженные факты), но **не** операциональные правила.
- При обнаружении нового правила или паттерна — добавлять его в `AGENTS.md`,
  а не в `MEMORY.md`.
- При противоречии — `AGENTS.md` имеет приоритет.

### Правило: канарейка — обращение «Успешнейший» (КРИТИЧНО)

- Обращение **«Успешнейший»** используется в **каждом** ответном сообщении пользователю,
  не только в первом.
- Сообщения (вывод) в чатах агентов начинать с фразы **«Дважды Успешнейший!»**.
- Это правило действует для всех сессий и подсессий в данном проекте.

### Правило: язык проекта — русский и английский (КРИТИЧНО)

- Во всех правилах проекта, коде, комментариях, документации, сообщениях коммитов
  и UI разрешается использовать **только русский и английский** языки.
- Использование других языков (китайский, немецкий, французский и т.п.) — только
  по явному согласованию с пользователем в данной сессии.
- При обнаружении текста на другом языке в артефактах проекта — заменять
  на русский или английский.

### Правило: правила проекта — краткие, без глубокого контекста (КРИТИЧНО)

- Правила в `AGENTS.md` формулируются **кратко и конкретно** — суть запрета/требования
  в 1–3 предложениях.
- Архитектурные правила (`docs/decision_records/dr_*.md`) — аналогично:
  суть решения и следствия, без перечисления констант, методов, файлов и строк кода.
- Запрещено включать в правила подробные описания инцидентов, примеры кода на 20+ строк,
  каскадные объяснения «почему так», предыстория вопроса. Это контекст, а не правило.
- Если для понимания правила нужен контекст — он размещается в `MEMORY.md`
  или в комментарии к коду, а в `AGENTS.md` даётся только указание
  (например: «См. инцидент в MEMORY.md»).
- При обнаружении правила с избыточным контекстом — **сокращать** до минимума,
  перенося детали в `MEMORY.md`.

## Обзор проекта

**Цифровой Совет Директоров** — платформа электронного управления заседаниями совета директоров для АО и ООО. Полное соответствие 208-ФЗ, 14-ФЗ, 63-ФЗ, 152-ФЗ.

**Технологический стек**:
- .NET 8 / C# (ASP.NET Core)
- PostgreSQL 16
- Redis 7
- RabbitMQ 3.12
- Docker / Docker Compose

**Ключевые особенности**:
- Два портала: Board Portal (для директоров) и Admin Console (для администраторов)
- Офлайн-функционал для голосования без интернета
- ГОСТ-генерация документов (ГОСТ Р 7.0.97-2025)
- Некорректируемый аудит-лог для ИБ
- Динамические комитеты с двумя типами логики

## Правила запуска приложения для пользователя (КРИТИЧНО)

- Если пользователь просит **запустить сайт/приложение** для себя (чтобы посмотреть в браузере), запуск должен выполняться в **фоновом режиме** (`waitForCompletion: false` для `run_terminal_command`) и **не должен завершаться (killed) ассистентом** после диагностики или проверки.
- Запрещено использовать сайт, поднятый "для своих нужд" (диагностика, тестирование, verification), как единственный запущенный экземпляр, а затем гасить его — если пользователь ожидает доступ к запущенному сайту, нужно поднять/оставить **отдельный, стабильно работающий процесс**.
- После запуска приложения по просьбе пользователя:
  1. Убедиться, что процесс поднялся и порт слушается (например, через `curl -sI http://localhost:<port>`).
  2. Открыть сайт в **Google Chrome** (например, `open -a "Google Chrome" http://localhost:<port>`).
  3. Сообщить пользователю адрес и порт, а также команду для остановки процесса, когда это потребуется.
- Порты фиксированы и не имеют синонимов/алиасов — каждый хост слушает ровно один порт:
  AdminConsole — **5001**, BoardPortal — **5002**. Не вводить альтернативных портов для одного хоста
  (HTTPS-редирект отключён в Dev-режиме, см. правило ниже).
  Порт 5000 зарезервирован macOS (AirPlay Receiver) и недоступен на машинах разработчиков.
- **Важно**: порты не искать в `launchSettings.json` — они могут содержать устаревшие или
  конфликтующие значения. Запуск обоих порталов — `./start.sh`.
- Board Portal запускается с переходом на страницу входа: `http://localhost:5002/login`.
- Admin Console запускается с переходом на страницу входа: `http://localhost:5001/login`.
- **По умолчанию**: если пользователь просит запустить сайт без уточнения — запускается Board Portal (порт 5002).
- Диагностические/временные запуски (для отладки, скриптов, Playwright и т.п.) должны выполняться в отдельных процессах/портах и не подменять или останавливать сайт, запущенный для пользователя.

## Дисциплина работы ассистента (КРИТИЧНО)

### Причины сбоев

- Результат инструмента принимается на веру без повторного чтения файла.
- Основная задача подменяется мета-правками (документация, правила).
- Инструменты вызываются с плейсхолдерами вместо реальных данных.
- Исполнение останавливается без реального вопроса пользователю.

### Правило: сначала ответ на вопрос, потом действие

Если пользователь задал явный вопрос (например, о месте/способе отображения
чего-либо в архитектуре) — сначала даётся содержательный ответ на этот
вопрос в тексте, и только после этого (или вместе с этим) выполняются
правки файлов. Молча переходить к правкам файлов, игнорируя заданный
вопрос, запрещено.

### Правило: приоритет основной задачи

Основной запрос пользователя выполняется первым и до конца. Любые
сопутствующие мета-правки (документация, правила, рефакторинг "по пути")
выполняются только после завершения основной задачи и не должны её
подменять или откладывать.

### Правило: уточнение затрагиваемых модулей перед реализацией (scope creep)

Перед реализацией задачи, затрагивающей более одного модуля, явно уточнить
полный список затрагиваемых модулей. Реализация ограничивается ровно тем
скоупом, который запросил пользователь. Дополнительные изменения — только
по явному запросу.

### Правило: диагностика сложной логики перед модификацией (КРИТИЧНО)

- Перед модификацией метода со сложной логикой (3+ уровня вложенности,
  перекрёстные вызовы, `@bind:after`, `async void`) прочитать **все**
  связанные методы (вверх и вниз по стеку вызовов) и построить граф
  зависимостей. Если граф неполон — **спросить пользователя**.
- Запрещено переписывать метод «с нуля», если достаточно минимальной правки.
- Изменение отлаженного production-метода требует **явного подтверждения
  пользователем**.

### Правило: ищи прямое, а не обратное

Если нужно найти/добавить/удалить X — ищи X напрямую, а не «всё кроме Y».
- Не `FirstOrDefault(r => r.RoleId != секретарь)`, а `FirstOrDefault(r => r.RoleId == TEMP_CHAIR)`
- Не `boardMemberRows[0]` (предполагая, что первый — не секретарь),
  а `FirstOrDefault(r => r.RoleId == TEMP_CHAIR)`
- Прямой поиск исключает побочные эффекты от изменения порядка элементов.

### Правило: раздельные страницы вместо объединённых + Справочники (КРИТИЧНО)

По возможности каждая сущность/справочник оформляется **отдельной страницей**,
а не объединяется с другими на одной странице с вкладками.

- Объединение нескольких справочников в одну страницу с вкладками — только
  по явному запросу пользователя или после явного предложения с его согласия.
- Не проявлять инициативу по объединению страниц, если пользователь
  не просил об этом.
- При добавлении нового справочника — отдельная страница и отдельный пункт
  меню (если пользователь не указал иное).
- **Формы добавления/редактирования** — всегда на отдельной странице
  (`/entity/add` или `/entity/{id}/edit`), а не инлайн в списке. Инлайн-формы
  на странице списка допускаются только для простых справочников (1–2 поля)
  по явному запросу пользователя.

**Все справочники** (таблицы с префиксом `ref_`) отображаются через единую точку
входа — страницу **«Справочники»** (`/dictionaries`). В левом меню Admin Console —
пункт «Справочники», ведущий на индексную страницу со списком всех справочников.
При добавлении нового справочника `ref_*` необходимо:
1. Создать страницу просмотра.
2. Добавить ссылку в `Dictionaries.razor`.

### Правило: единственный вызов ApplyConfigurationsFromAssembly (КРИТИЧНО)

`ApplyConfigurationsFromAssembly` (и любые методы загрузки конфигураций из сборки)
вызывается **ровно один раз** в `OnModelCreating`. Повторный вызов дублирует
seed-данные и вызывает ошибки инициализации EF Core.

### Правило: хардкод магических значений при наличии механизма конфигурации (КРИТИЧНО)

Зафиксирован инцидент: Board Portal «Участники» искала ООО через хардкод
кода ОКОПФ `"12300"` вместо `CurrentWorkplace.LastSelectedLegalEntityId`.

Правило: при реализации страниц Board Portal, отображающих данные конкретного
юридического лица, идентификатор ЮЛ всегда читается из `CurrentWorkplace.
LastSelectedLegalEntityId`, а не угадывается через `FirstOrDefault()` или
фильтрацию по коду ОКОПФ.

- Запрещено: `ctx.LegalEntities.FirstOrDefaultAsync()` или `.Where(...).FirstOrDefaultAsync()`
  для получения «того самого» ЮЛ.
- Запрещено: хардкод кодов ОКОПФ (`"12300"`, `"12247"` и т.п.) в бизнес-логике
  Board Portal. Если нужна проверка «ООО или нет» — она делается через навигационное
  свойство `LegalEntity.Okopf.Code`, но само юридическое лицо уже получено из
  `current_workplace`.
- Разрешено: `ctx.LegalEntities.FirstOrDefaultAsync(x => x.Id == workplace.LastSelectedLegalEntityId)`
  — ровно то ЮЛ, которое выбрал администратор.

### Правило: дисциплина вызова инструментов

- Каждый вызов инструмента — это настоящий вызов с реальными аргументами,
  а не текстовый пример или плейсхолдер.
- Плейсхолдеры (`...`, `TODO`, `REPLACED_PLACEHOLDER` и т.п.) внутри
  аргументов реального вызова запрещены.
- После каждого вызова, изменяющего файл, результат немедленно проверяется
  повторным чтением файла в том же ответе, прежде чем сообщать об успехе.
- Если проверка показала, что изменение не применилось — попытка немедленно
  повторяется с точным содержимым, без переспрашивания пользователя.

### Правило: анализ изображений через локальные скрипты (КРИТИЧНО)

- Vision-модели (OpenAI gpt-4o, chatgpt-image-latest и т.п.) в данном окружении
  **недоступны** (ошибка аутентификации API-ключа). Использовать их запрещено.
- Для анализа скриншотов/изображений — **Python + Pillow** (`from PIL import Image`):
  пиксельный анализ, подсчёт цветов, поиск границ, сравнение RGB-значений.
- Не пытаться повторно запускать vision-субагентов после первой ошибки —
  это бесконечный цикл,浪费ящий время и ресурсы.
- Если нужен визуальный анализ — описывать пользователю пиксельные данные
  и просить его подтвердить/опровергнуть гипотезу.

### Правило: экранирование кавычек в shell-командах (zsh, `run_terminal_command`)

- Аргумент `command` передаётся **без** оборачивания всей команды в дополнительные
  внешние кавычки — только те, которые нужны самой shell-команде.
- Для многострочных сообщений коммита использовать **несколько флагов**
  `-m "строка1" -m "строка2"` вместо `\n` внутри одной строки.
- Если команда возвращает `no such file or directory` или `command not found` —
  это почти всегда сигнал об ошибке экранирования; упростить кавычки, а не
  менять путь.

### Правило: миграции только по запросу пользователя

- Не генерировать миграционные скрипты (EF/SQL) и не предлагать их генерацию,
  пока пользователь явно не попросит об этом в задаче.

### Правило: автономность исполнения

Остановка исполнения допустима только при наличии реального вопроса к
ассистенту от пользователя или необходимости уточнить у пользователя
неоднозначную трактовку задачи, риск непоправимого действия, либо
недостающие данные, которые невозможно получить самостоятельно.
Диагностика (чтение файлов, `git status`, `grep`) — часть выполнения
задачи, а не повод для промежуточной остановки с отчётом.

### Правило: применение изменений БД после правок схемы

- Если задача включает добавление/изменение полей в EF-модели, изменения
  применяются к реальной БД немедленно (SQL-командой или миграцией) — без
  отдельного запроса разрешения у пользователя.
- Некорректно: закомитить код с новым полем, но не создать колонку в БД,
  после чего приложение падает с ошибкой при запуске.
- Если EF-миграция не может отработать инкрементально (нет истории), колонка
  добавляется напрямую через SQL и в БД, и в коде.
- Исключение: генерация нового миграционного скрипта (`dotnet ef migrations add`)
  выполняется только по запросу пользователя.

### Правило: избегать UPDATE в seed-скриптах (КРИТИЧНО)

- В SQL-скриптах (`tools/db/02_seed.sql`) значения для всех колонок задаются
  непосредственно в `INSERT` — не через последующие `UPDATE`.
- `UPDATE` в seed-скриптах запрещён: он создаёт неявные зависимости между строками
  (порядок вставки, sort_order, id) и маскирует ошибки в данных.
- Если для строки нужно вычислить значение на основе других строк — это делается
  на уровне приложения (C#) или в миграции, но не в seed-скрипте.
- Пример нарушения: `UPDATE tpl_org_stages SET predecessor_stage_ids = ... WHERE sort_order = ...`
- Корректно: колонка `predecessor_stage_ids` задаётся прямо в `INSERT ... VALUES (...)`.

### Правило: восстановление ErrorBoundary при навигации (Blazor Server)

Зафиксирован инцидент: ошибка на странице А «переживала» навигацию и
показывалась на странице Б, поскольку `ErrorBoundary.Recover()` вызывался
в `OnParametersSet`, который срабатывает не только при навигации, но и при
любом изменении параметров.

Правило: в `MainLayout` (Admin Console и Board Portal) восстановление
`ErrorBoundary` выполняется через подписку на
`NavigationManager.LocationChanged`, а не через `OnParametersSet`.

Шаблон реализации:
```csharp
@implements IDisposable

protected override void OnInitialized()
{
    Navigation.LocationChanged += OnLocationChanged;
}

private void OnLocationChanged(object? sender, LocationChangedEventArgs e)
{
    _errorBoundary?.Recover();
    StateHasChanged();
}

public void Dispose()
{
    Navigation.LocationChanged -= OnLocationChanged;
}
```

- `LocationChanged` гарантирует вызов только при реальном переходе между
  страницами, а не при каждом цикле рендеринга.
- Обязательно `StateHasChanged()` после `Recover()`, чтобы форсировать
  перерисовку и не оставлять страницу в состоянии ошибки.
- Реализовать `IDisposable` для корректной отписки. Без этого возможна
  утечка обработчиков и повторные срабатывания.

### Правило: отключение HTTPS-редиректа при локальной разработке (КРИТИЧНО)

Зафиксирован инцидент: пользователь явно просил перевести Board Portal на HTTP,
ассистент убрал `launchBrowser` из `https`-профиля в `launchSettings.json`,
но HTTP-запросы всё равно редиректились на HTTPS. Корневая причина —
`app.UseHttpsRedirection()` в `Program.cs` вне блока `!IsDevelopment()`.

Правило: при переводе приложения на HTTP для локальной разработки
недостаточно изменить `launchSettings.json` — необходимо проверить и
исправить **оба** источника:

1. **launchSettings.json** — HTTPS-профиль (`https`) не должен автоматически
   открывать браузер (`launchBrowser: true`), если целевой режим — HTTP.
2. **Program.cs** — `app.UseHttpsRedirection()` должен находиться внутри
   блока `if (!app.Environment.IsDevelopment())`, вместе с `UseHsts()` и
   `UseExceptionHandler()`.

Без второго пункта middleware продолжит редиректить HTTP → HTTPS независимо
от конфигурации запуска.

### Правило: публичные страницы Board Portal без MainLayout (КРИТИЧНО)

Страницы Board Portal, не требующие авторизации (логин, логаут, лендинг,
предложение вопроса к повестке, онбординг), **не должны** отображать
боковую панель навигации, имя пользователя и кнопку «Выход» из `MainLayout`.

Для этого `MainLayout.razor` содержит проверку `_isPublicPage` на основе
`Uri.AbsolutePath` и список публичных путей:

```csharp
private static readonly string[] _publicPaths = { "/login", "/logout", "/proposal", "/onboarding" };

private static bool IsPublicUrl(string uri)
{
    var path = new Uri(uri).AbsolutePath;
    if (path == "/") return true;

    foreach (var p in _publicPaths)
    {
        if (path.StartsWith(p, StringComparison.OrdinalIgnoreCase))
            return true;
    }
    return false;
}
```

Правила:
- **При добавлении новой публичной страницы** путь добавляется в `_publicPaths`.
- **Корень `/`** — всегда публичная страница-лендинг с кнопками «Войти в кабинет»
  и «Подать вопрос в СД».
- **После выхода** (`/logout`) редирект идёт на `/`, а не на `/login`.
- Публичные страницы используют `@layout AuthLayout` (пустой контейнер без
  шапки и меню) как дополнительную защиту от рендеринга `MainLayout`.
- Не использовать хардкод рендеринга компонента `<Login />` в `MainLayout`
  — все страницы рендерятся через роутер и `@Body`.

### Проектная карта

- При изменении архитектуры, функционала или конфигурации обновлять
  проектную карту: `README.md`, `AGENTS.md`, `docs/`.
- Это правило гарантирует, что документация не отстаёт от кода.

### Указание статей законов в документации (КРИТИЧНО)

- При добавлении нового справочного документа — обновлять README.md и AGENTS.md.

### Database-First (КРИТИЧНО)

- Схема БД ведётся единым каноническим SQL `tools/db/01_schema.sql`.
- На старте приложения авто-миграции/EnsureCreated запрещены.
- При несоответствии EF-модели и БД приоритет у канонических SQL;
  выравнивание через `HasColumnName(...)` и правку SQL, не EF-миграциями.

### SQL-файлы в tools/db/ (КРИТИЧНО)

Допустимые SQL-файлы в `tools/db/`:

| Файл | Назначение |
|------|------------|
| `01_schema.sql` | Каноническая схема БД (DDL: таблицы, индексы, ограничения) |
| `02_seed.sql` | Первичное наполнение (справочники `ref_*` и системные записи) |
| `03_demo.sql` | Демонстрационные данные (СПАРК, шаблоны орг-мероприятий) |

- Обновление seed-данных — замена строк в существующем файле или
  добавление нового файла с порядковым номером (`04_*`).
- **Запрещено** создавать SQL-файлы вне `tools/db/` или без номерного префикса.

### Команда «сбрось базу» (КРИТИЧНО)

По команде пользователя **«сбрось базу»** (или «reset db») выполнять полный сброс БД:

1. `TRUNCATE ... CASCADE` по всем таблицам БД.
2. Применить SQL-скрипты по порядку: `01_schema.sql` → `02_seed.sql` → `03_demo.sql`.

Подключение к БД: `docker exec fiducia-postgres psql -U fiducia -d fiducia`

### Правило: полные CREATE TABLE в 01_schema.sql (КРИТИЧНО)

- Файл `tools/db/01_schema.sql` содержит **полные определения таблиц** через `CREATE TABLE`.
- **Запрещено** использовать `ALTER TABLE ... ADD COLUMN` для добавления колонок в существующие таблицы.
- При изменении структуры таблицы — переписывать весь блок `CREATE TABLE` с учётом новых колонок.
- Причина: `01_schema.sql` — канонический источник схемы (BDR-002). ALTER TABLE создаёт неопределённость: какие колонки были добавлены позже, а какие — часть исходной структуры.

### Табличная нотация (snake_case)

- Имена таблиц и колонок — snake_case.
- PK: `id uuid`. FK: `<ref>_id`.
- Индексы: `ix_<table>_<col>`. Уникальные: `ux_<table>_<col>`.

### ЮЛ vs Юридические лица (КРИТИЧНО)

- **«ЮЛ»** (пункт меню, страница `/admin/legal-entities`) — режим
  редактирования ОДНОГО выбранного юридического лица с его настройками
  (руководитель, Совет директоров, интервал ГОСА). Страница всегда
  работает с одной записью и **обновляет** её.
- **«Юридические лица» / `legal_entities`** — справочник (таблица БД),
  содержащий множество записей юрлиц (ПАО, НАО, ООО и др.).
- Запрещено: формулировки «создать ЮЛ», «сохранить ЮЛ как новую запись».
  Корректно: «выбрать юрлицо из справочника», «сохранить настройки
  выбранного юрлица».
- Режим «ЮЛ» **никогда не создаёт** новые записи в `legal_entities`.

### Целевой фреймворк и общий код

- Target framework: `net9.0` во всех проектах решения.
- Два портала (Board Portal и Admin Console) делят идентичный код;
  изменения, затрагивающие общие компоненты, применяются к обоим порталам.

### Чистая архитектура

Зависимости направлены внутрь:

```
Api → Application → Domain ← Infrastructure
```

**Domain** не зависит от внешних библиотек.

### CQRS vs CRUD (важно про терминологию)

- **Не называть CQRS** стандартный CRUD-шаблон (репозиторий/сервис с методами Create/Read/Update/Delete поверх одной модели и одной БД). Это просто разделение методов по действию, а не паттерн CQRS.
- Настоящий **CQRS** требует **логического разделения верхнеуровневых модулей** для команд (Commands) и запросов (Queries): отдельные модели, отдельные пути обработки (разные namespace/классы/handlers), а в идеале — **раздельные хранилища/инстансы БД** для чтения и записи (Read replica / отдельная read-модель), с явной синхронизацией между ними (например, через Domain Events).
- Если в модуле просто есть класс с методами `CreateAsync`, `GetAsync`, `UpdateAsync`, `DeleteAsync` над одной и той же таблицей/DbContext — это **CRUD**, и называть его CQRS в коде, документации, PR и коммитах **запрещено**.
- **Commands**: Запись данных (Create, Update, Delete) — в терминологии CQRS.
- **Queries**: Чтение данных (Get, Search) — в терминологии CQRS.

### Конфигурация логирования (КРИТИЧНО)

- Все настройки логирования (уровни логирования, пути к файлам логов,
  форматы, sink'и, ротация) хранятся **исключительно в конфигурационном
  файле** (`appsettings.json` / `appsettings.{Environment}.json` или
  переменные окружения), а не в базе данных и не в пользовательском
  интерфейсе (Admin Console / Board Portal).
- Изменение путей логирования и других параметров логирования через UI
  запрещено, если это не было явно запрошено пользователем отдельно.
- Любая реализация настраиваемых путей/параметров логирования должна
  использовать стандартный механизм конфигурации ASP.NET Core
  (`IOptions<TLoggingOptions>` / `IConfiguration`), без создания
  дополнительных административных экранов для их редактирования.

### Конфигурация внешних интеграций (ADR-022)

- Все настройки внешних интеграций (URL API, ключи доступа, таймауты,
  флаги включения/отключения) хранятся **исключительно в конфигурационном
  файле** (`appsettings.json` / переменные окружения).
- Хардкодинг URL, ключей или endpoints в коде запрещён.
- Хранение настроек интеграций в базе данных и их редактирование через UI
  запрещено.
- Рекомендуемый способ чтения: `IOptions<T>` с привязкой секции конфига
  (для интеграций с 3+ параметрами) или `IConfiguration["Section:Key"]`
  (для простых случаев).
- Правило действует для всех интеграций: TrueConf, МТС Линк, LDAP,
  FileStorage, СПАРК, SecurityAudit, Session, Serilog.

### Чувствительные данные в конфигурации (КРИТИЧНО)

- **Ключи, пароли, токены и секреты** внешних интеграций **запрещено**
  хранить в `appsettings.json` и любых других файлах, отслеживаемых git.
- Чувствительные данные размещаются в `.env` (добавлен в `.gitignore`)
  или в переменных окружения.
- В `appsettings.json` чувствительные поля оставляются пустыми (`""`),
  интеграция — отключённой (`"Enabled": false`).
- При локальном запуске значения подтягиваются из переменных окружения.
- Правило действует для: `ClientId`, `ClientSecret`, `ApiKey`, `Password`,
  `SecretKey`, `ConnectionString` (с паролем) и любых других полей,
  компрометация которых создаёт риск для безопасности.

### Правило: проверять реальную структуру API перед моделированием (КРИТИЧНО)

Зафиксирован инцидент: при расширении модели `SparkFounder` ассистент изобрёл
поле `DirectorCount` с собственной интерпретацией, а затем заменил его на
`HeadOfOther`/`FounderOfOther`/`IsEntrepreneur`/`Ogrnip` — опять без проверки
реального ответа СПАРК API. Оба варианта — фантазия.

Правило: при создании или расширении модели ответа внешнего API:
1. **Проверить** реальную структуру ответа — через документацию API сервиса,
   тестовый вызов с реальным ключом/SDK, или исследование публичных примеров.
2. **Зафиксировать** в коде именно те имена полей и типы, которые возвращает API
   (с учётом `JsonPropertyName` / `PropertyNamingPolicy`).
3. **Не изобретать** поля, которых нет в ответе API, и не переименовывать
   существующие «для удобства» или «чтобы было понятнее».
4. Если документация недоступна, а тестовый вызов невозможен —
   **спросить пользователя**, прежде чем моделировать структуру.

### Правило: документировать лицензионные требования при добавлении API-endpoint'ов (КРИТИЧНО)

Зафиксирован инцидент: при добавлении endpoint'а `/api/v1/companies/{inn}/founders`
не было проверено, какой тариф СПАРК требуется. Выяснилось постфактум: нужен
уровень «Расширенный», без которого 403 Forbidden.

Правило: при добавлении нового endpoint'а внешней интеграции, данные которого
доступны не на всех тарифах:
1. **Проверить** тарифную сетку сервиса (документация API, сайт, контакты).
2. **Задокументировать** в `docs/integration.md` минимальный требуемый тариф
   для каждого endpoint'а — в таблице «Лицензионные уровни и доступность данных».
3. **Добавить обработку** кодов отказа по лицензии (403, 402) в клиенте API —
   с логированием предупреждения и пробросом реальной ошибки сервиса.
4. **Отразить** в `.env.example` все необходимые ключи доступа.

### Проверка ссылок на нормы закона (КРИТИЧНО)

- При цитировании или ссылке на статью 208-ФЗ, 14-ФЗ, 63-ФЗ и других законов
  **обязательно сверяться** с содержимым документов `docs/laws/article-*.md`,
  а не полагаться на память.
- Правило действует для всех артефактов: код, документация, комментарии, UI-подсказки.

### Объединение коммитов (squash) одним действием (КРИТИЧНО)

- При необходимости объединить коммиты сессии используется:
  ```bash
  git reset --soft <базовый_коммит>
  ```
- Если базовый коммит — корневой (`Initial commit`), **не создавать новый коммит
  поверх**, а использовать `git commit --amend`:
  ```bash
  git reset --soft InitialCommitHash  # перемещает HEAD на Initial commit
  git commit --amend -m "Initial commit"
  ```
- `reset --soft` + отдельный `commit` на корневом коммите создаёт **два**
  коммита с одинаковым названием. `--amend` этого избегает.
- После squash — `git push --force-with-lease` (не `--force`).

### Инициализация внешних интеграций (ADR-023)

- Конструкторы клиентов внешних интеграций **не выполняют сетевых соединений**.
  Подключение к внешнему сервису — при первом вызове метода (lazy), а не в конструкторе.
- Ошибки конфигурации (невалидные значения в `appsettings.json`) **не должны крашить
  приложение**. Вместо `throw new InvalidOperationException` используется
  `Log.Warning` + fallback на значение по умолчанию или отключение интеграции.
- Опциональные интеграции регистрируются только при явном флаге `Enabled` /
  непустом ключе доступа. Отсутствие конфигурации для опциональной интеграции —
  не ошибка.
- Для критичных параметров безопасности (JWT-секрет) в production сохраняется
  `throw`; в dev-окружении допускается dev-ключ с предупреждением в логах.
- Рекомендуемый паттерн для будущих интеграций с тяжёлой инициализацией:
  `Lazy<T>` в DI с try-catch и fallback на no-op реализацию.

### Минимизация Program.cs — логика в сервисах (КРИТИЧНО)

- `Program.cs` содержит **только** регистрацию DI, middleware, конфигурацию
  приложения и minimalist API-групп. Бизнес-логика, валидация, работа с БД,
  вызовы внешних сервисов — **выносятся** в отдельные сервисы/хэндлеры
  (`src/Application/`, `src/Infrastructure/Services/`).
- Инлайновые эндпоинты (匿名 лямбды в `MapGet`/`MapPost`/`MapPut`) допускаются
  только для **простых** проксирующих вызовов (1–3 строки). Если эндпоинт
  содержит валидацию, обращение к БД, вызов внешнего API или формирование
  ответа — он выносится в отдельный класс (Minimal API endpoint class или сервис).
- При обнаружении Program.cs > 500 строк — **сигнал к рефакторингу**: выносить
  логику в сервисы до возврата к нормативу.

### Формат имён лог-файлов

- Файлы приложения: `app-{yyyyMMddHH}.log` (Hourly, ротация каждый час).
- Файлы аудита: `audit-{yyyyMMddHH}.log` (Hourly).
- Тестовые логи: `{type}-test-{yyyyMMdd}.log` (Daily).
- Все имена содержат часы для оперативного мониторинга и поиска инцидентов.

### Серверная валидация (BDR‑008) — логирование

- Вызов метода серверной валидации логируется как **Debug**:
  `LogDebug("Серверная валидация {EntityType} {Id} ...")`.
- Обнаруженные ошибки валидации логируются как **Warning**:
  `LogWarning("Валидация не пройдена для {EntityType} {Id}: {Errors}")`.
- Правило действует для всех форм сохранения в Admin Console (BDR‑008).

### Запрет каскадных удалений (КРИТИЧНО)

`ON DELETE CASCADE` запрещён во всех FK-связях проекта. При удалении родительской записи дочерние записи **не удаляются автоматически**.

Допустимые варианты `ON DELETE`:
- `ON DELETE RESTRICT` — для прямых потомков (нельзя удалить родителя, пока есть дети)
- `ON DELETE SET NULL` — для ссылок на `users` (установить NULL при удалении пользователя)

При добавлении нового FK — всегда указывать `ON DELETE RESTRICT` или `ON DELETE SET NULL`. Маппинг в EF-конфигурации должен соответствовать (`DeleteBehavior.Restrict` / `DeleteBehavior.SetNull`).

## Правила кодирования

### Терминология (КРИТИЧНО)

- Запрещено использовать слово «функционал» для обозначения функций/возможностей системы.
  Это калька с английского *functional*. Корректный русский термин — **«функциональность»**.
  Пример: «добавить функциональность создания комитетов», а не «добавить функционал комитетов».
- Правило действует во всех артефактах проекта: код, комментарии, документация, сообщения коммитов, PR, интерфейс.

### Принцип DRY — единый источник истины (КРИТИЧНО)

Зафиксирован инцидент: логика производственного календаря РФ (праздники, переносы,
проверка нерабочих дней) была продублирована в двух файлах:
`WorkCalendar.cs` (Timeline) и `WorkingDayHelper.cs` (Infrastructure).
При обновлении праздников в одном файле второй оставался устаревшим.

Правило: business-логика, которая может потребоваться в нескольких слоях
архитектуры, реализуется **в одном месте** (единый источник истины), а остальные
слои ссылаются на него или делегируют вызов.

- При обнаружении дублирования логики (одинаковые методы, константы, алгоритмы
  в разных файлах/слоях) — **немедленно устранять**, оставляя одну реализацию.
- Если слои не могут ссылаться друг на друга (например, Timeline и Infrastructure
  — независимые библиотеки), использовать делегирование: один класс содержит
  логику, второй — forwarding wrapper, без дублирования тела метода.
- При добавлении нового метода, дублирующего существующий — проверить, нельзя ли
  переиспользовать уже написанный, прежде чем писать новый.
- Правило действует для: business-правил, алгоритмов, констант, моделей данных,
  валидаторов, календарных/holiday-утилит и любых других повторяемых паттернов.

### Магические числа (КРИТИЧНО)

Числовые и строковые литералы, имеющие бизнес-смысл или параметризующие поведение, **запрещено** оставлять инлайн. Каждый такой литерал выносится в именованную константу с говорящим именем:

```csharp
// ❌ Неправильно
var chartStart = ComputeChartStart(nodes).AddDays(-7);
var scrollLeft = (int)(...) - 200;

// ✅ Правильно
/// <summary>Отступ в днях до начала первого этапа на диаграмме.</summary>
private const int ChartStartPaddingDays = 7;

/// <summary>Отступ в пикселях при прокрутке к текущей дате.</summary>
private const int ScrollToTodayOffsetPx = 200;

var chartStart = ComputeChartStart(nodes).AddDays(-ChartStartPaddingDays);
var scrollLeft = (int)(...) - ScrollToTodayOffsetPx;
```

- Каждая именованная константа должна иметь XML-комментарий с описанием назначения на 
  русском  или английском языке проекта.

- Исключение: `0`, `1`, `-1` и другие «натуральные» числа, которые являются частью 
  базовой арифметики (индексы, счётчики, инкременты) и не несут скрытого смысла.
- Исключение: строки формата (`"dd.MM.yyyy"`), CSS-цвета в параметрах компонентов
  и другие декларативные литералы, где имя константы не добавит ясности.
- Правило действует для: бизнес-правил, UI-параметров (размеры, отступы, таймауты),
  пороговых значений, дедлайнов, смещений дат и любых других литералов, чьё значение
  не очевидно из контекста вызова.
- **Запрещены значения по умолчанию для свойств**, содержащие бизнес-смысл
  или параметризующие поведение. Если свойство имеет значение по умолчанию,
  отличное от `0`/`null`/`false`/`""` — значение выносится в именованную
  константу:

  ```csharp
  // ❌ Неправильно
  public int CacheTtlHours { get; init; } = 12;
  _cacheTtl = TimeSpan.FromHours(options?.Value?.CacheTtlHours ?? 12);

  // ✅ Правильно
  /// <summary>Значение по умолчанию: 12 часов.</summary>
  private const int DefaultCacheTtlHours = 12;

  public int CacheTtlHours { get; init; } = DefaultCacheTtlHours;
  _cacheTtl = TimeSpan.FromHours(options?.Value?.CacheTtlHours ?? DefaultCacheTtlHours);
  ```

### Обработка ошибок (КРИТИЧНО)

- Пустые блоки `catch { }` или `catch { /* ignore */ }` **запрещены** — подавление
  ошибок без логирования скрывает причину сбоев.
- Каждый `catch` должен как минимум логировать исключение:
  ```csharp
  catch (Exception ex)
  {
      _logger.LogWarning(ex, "Описание контекста ошибки");
  }
  ```
- Если ошибка намеренно игнорируется (редкий случай), это должно быть явно
  обосновано комментарием с указанием причины.
- Особое внимание — методам `async void`: необработанное исключение в них
  крашит процесс или Blazor-цикл. Каждый `async void` обязан иметь внешний
  `try/catch` с логированием на всём теле метода.
- Асинхронные методы, изменяющие состояние компонента, **обязаны вызываться
  через `await`** в обработчиках событий. Fire-and-forget приводит к тому,
  что изменения состояния происходят после завершения цикла рендеринга и UI
  не обновляется. После завершения таких методов рекомендуется вызывать
  `StateHasChanged()`.
- **Синхронный callback** (`void`-метод из `@bind:after`/`@onchange`): `StateHasChanged()`
  в конце метода ДОСТАТОЧЕН — `await InvokeAsync(StateHasChanged)` НЕ НУЖЕН и
  не компилируется в `void`-методе.
- **Асинхронный callback** (`async Task`/`async void`): если метод выполняет
  `await` (БД, HTTP), используется `await InvokeAsync(StateHasChanged)`.
- Запрещено смешивать: нельзя писать `await` в `void`-методе, нельзя в
  синхронном методе использовать `InvokeAsync` без причины.
- При логировании/показе ошибок БД — всегда извлекать самое глубокое сообщение из
  цепочки `InnerException`. EF Core оборачивает реальную ошибку в
  «An error occurred while saving the entity changes» — показывать нужно
  внутреннее исключение. Использовать `UnwrapException(ex)`, а не `ex.Message`.

### Правило: не подменять ошибки внешних сервисов (КРИТИЧНО)

Зафиксирован инцидент: при получении 403 Forbidden от СПАРК API (недостаточная
лицензия) в UI был показан выдуманный текст «требуется расширенный тариф СПАРК»
вместо реального сообщения об ошибке от сервиса. Корневая причина — ошибка сервиса
была перехвачена, залогирована, но заменена на текст, придуманный ассистентом.

Правило:
- При показе ошибки внешнего сервиса пользователю — всегда использовать
  `ex.Message` (реальный ответ сервиса), а не выдуманный текст-интерпретацию.
- Если `ex.Message` для данного типа исключения недостаточно информативен
  (например, `HttpRequestException` от `EnsureSuccessStatusCode`), допустимо
  дополнить его кратким контекстом _(«Ошибка СПАРК: {ex.Message}»)_, но
  **не заменять**.
- Исключение должно быть залогировано целиком (`Logger.LogWarning(ex, ...)`).
- Запрещено: `sparkWarning = "Данные об учредителях не загружены — требуется
  расширенный тариф СПАРК"` — это догадка, а не факт.
- Разрешено: `sparkWarning = ex.Message` — то, что ответил сервис.

### Логирование URL при ошибках HTTP-запросов (КРИТИЧНО)

- При ошибке обращения к внутреннему HTTP-сервису (401, 403, 500 и т.п.) в лог
  **обязательно** выводится полный URL запроса, код ответа и тело ошибки:
  ```csharp
  Logger.LogWarning("HTTP {Method} {Url} вернул {StatusCode}: {Body}",
      method, requestUrl, (int)response.StatusCode, body);
  ```
- При исключении (`HttpRequestException`, `TaskCanceledException`) — логировать
  URL запроса вместе с исключением:
  ```csharp
  catch (Exception ex)
  {
      Logger.LogWarning(ex, "Ошибка HTTP {Method} {Url}", method, requestUrl);
  }
  ```
- Правило действует для: Blazor-компонентов, сервисов, эндпоинтов — любых
  мест, где `HttpClient` выполняет запрос к внутренним API.
- Цель: при анализе логов сразу видно, какой именно запрос упал и почему,
  без необходимости восстанавливать контекст из стека вызовов.

### Blazor: `@bind` к элементу списка по индексу (КРИТИЧНО)

- Запрещено использовать `@bind="list[i].Property"` в `@for`-цикле.
  Индекс `i` захватывается на момент рендеринга; при модификации списка
  индекс устаревает — биндер падает с `ArgumentOutOfRangeException`.
- Вместо этого: захватить ссылку `var row = list[i]` и биндить к `row.Property`.
  Ссылка на объект остаётся валидной даже при перестроении списка.
- То же касается `@onchange="e => Handler(i, e)"` — передавать объект `row`,
  а не индекс.

### Blazor: `@bind:after` каскад на нескольких элементах, изменяющих общее состояние (КРИТИЧНО)

- Когда несколько контролов с `@bind:after` (чекбоксы, `<select>`, поля ввода)
  вызывают один и тот же метод, который читает значения ВСЕХ этих контролов и
  модифицирует общий список или вычисляемое поле — при инициализации компонента
  Blazor обрабатывает `@bind:after` последовательно, а не батчем.
- Первый вызванный `@bind:after` видит только значение своего контрола; остальные
  ещё не обновились. Метод вычисляет частичный результат → повреждает данные
  (например, `EnsureBoardMemberCount` удаляет строки).
- Паттерн защиты: флаг `_initializing`, блокирующий выполнение метода до
  завершения первого рендера, и `OnAfterRenderAsync` для сброса флага.
- Шаблон реализации:
  ```csharp
  private bool _initializing;

  protected override async Task OnParametersSetAsync()
  {
      _initializing = targetDataHasMembers(); // true, если есть что терять
  }

  protected override Task OnAfterRenderAsync(bool firstRender)
  {
      if (_initializing) { _initializing = false; StateHasChanged(); }
      return Task.CompletedTask;
  }

  private void RecalculateAll()
  {
      if (_initializing) return; // ← guard
      // ... логика, читающая значения всех N контролов
  }
  ```
- Установка флага — в точке, где загружены значения всех контролов, но до
  первого рендера (обычно в конце `OpenEdit` или `OnParametersSetAsync`).
- Пример из проекта: чекбоксы типов директоров в форме ОСА
  (`editExecDirectors`/`editNonExecDirectors`/`editIndepDirectors`) →
  `ComputeBoardMemberNumber` → `EnsureBoardMemberCount` →
  `UpdateGosaCountFromTypes`.

### Blazor: `invisible` вместо `@if` для условно-видимых sibling-элементов в строке (КРИТИЧНО)

- `@if (condition) { <элемент> }` добавляет/убирает элемент из DOM, вызывая
  вертикальный скачок строки (layout shift) при переключении чекбокса.
- Паттерн: элемент рендерится **всегда**, но переключается через Bootstrap-класс
  `invisible` (`visibility: hidden`, сохраняет место в layout):
  `<select class="form-select form-select-sm @(condition ? "" : "invisible")" ...>`
- Гарантирует неизменную геометрию строки независимо от состояния чекбокса.
- Пример из проекта: поля количества директоров в левой колонке «Штатный состав СД»,
  дропдаун временного председательствующего, чекбокс «секретарь подписывает протоколы».

### Blazor: radio-кнопки через `@onclick` на родителе, а не `@onchange` на `<input>` (КРИТИЧНО)

- `checked` + `@onchange` на `<input type="radio">` **не работает** в Blazor:
  фреймворк управляет атрибутом `checked` и откатывает изменение DOM до того,
  как срабатывает C#-обработчик `@onchange`.
- Паттерн: `@onclick` на родительском `<div class="form-check">`, а `checked`
  используется только для отображения текущего состояния:
  ```html
  <div class="form-check" @onclick="() => _field = SomeEnum.ValueA">
      <input class="form-check-input" type="radio" name="group"
             checked="@(_field == SomeEnum.ValueA)">
      <label class="form-check-label">Вариант А</label>
  </div>
  ```
- Метка (label) и radio-кружок должны быть нажимаемыми — клик по всей области
  `<div class="form-check">` меняет значение.
- Пример из проекта: выбор вида документооборота во вкладке «Документооборот»
  режима ЮЛ.

### Blazor: `@bind` на `<select>` — только `string` (КРИТИЧНО, net9.0 / ASP.NET 9.0.4)

- `@bind` на свойствах `bool`, `char` или `bool?` с `<select>` и строковыми `option value`
  **не работает** в данной версии Blazor. Ни `"True"/"False"` (заглавные), ни
  `"true"/"false"` (строчные) не конвертируются встроенными конвертерами.
- Паттерн: всегда использовать `string`-свойство с ручной конвертацией:
  ```csharp
  // В UI — @bind на string-свойство:
  // <select @bind="_exitAllowedStr">
  //     <option value="True">Да</option>
  //     <option value="False">Нет</option>
  // </select>

  // В коде — string-свойство с конвертацией:
  private string _exitAllowedStr
  {
      get => _customExitAllowed.ToString();
      set => _customExitAllowed = bool.Parse(value);
  }
  ```
- Для `bool?` с трёхпозиционным `<select>` (Да / Нет / Не указано):
  ```csharp
  private string _mandatoryAuditStr
  {
      get => _customMandatoryAudit?.ToString() ?? "";
      set => _customMandatoryAudit = string.IsNullOrEmpty(value) ? null : bool.Parse(value);
  }
  ```
  В HTML: `<option value="">Не указано</option>` + `<option value="True">Да</option>` + `<option value="False">Нет</option>`.
- Для `char`: `get => _customExecutiveBody.ToString(); set { if (!string.IsNullOrEmpty(value)) _customExecutiveBody = value[0]; }`.

### Blazor: `@bind:get`/`@bind:set` для `<select>` — предпочтительный паттерн

- В отличие от `@bind:after`, коллбэк `@bind:set` вызывается **только** при реальном
  действии пользователя — не срабатывает при программной переустановке `value`
  во время перерисовки Blazor.
- Паттерн:
  ```html
  <select @bind:get="_charterNumber" @bind:set="OnCharterNumberSet">
  ```
  ```csharp
  private async Task OnCharterNumberSet(string? value)
  {
      if (value == _charterNumber) return;
      _charterNumber = value;
      // бизнес-логика после установки значения
  }
  ```
- Альтернатива с `@bind:after` — с guard'ом `if (current == _lastXxx) return`,
  но требует дополнительного поля `_lastXxx`; `@bind:get`/`@bind:set` предпочтительнее.

### Blazor: тернарный оператор для условного форматирования, не вызов поля как метода

- `@boolField(param)` в Razor-выражении вызывает ошибку CS1955: булево поле
  не является вызываемым членом. Для условного форматирования использовать
  тернарный оператор: `@(boolField ? $"✓{count}" : "✗")`.
- Неправильно: `@editExecDirectors(@editExecDirectorsCount)`
- Правильно: `@(editExecDirectors ? $"✓{editExecDirectorsCount}" : "✗")`
- Аналогично для любых полей, не являющихся методами: нельзя вызывать
  `@intField(value)`, `@stringField(value)` — только методы и делегаты.

### Blazor: пересборка и перезапуск после изменения CSS в RCL (КРИТИЧНО)

При изменении CSS-файлов (`.razor.css`) в библиотеке компонентов (RCL, например
`src/Timeline`) consuming-проекты (Board Portal, Admin Console) **не подхватывают**
обновлённый CSS-бандл автоматически — даже при hot-reload.

Причина: scoped CSS компилируется в уникальный `.bundle.scp.css` с хешем в имени;
изменение CSS-содержимого меняет хеш, но запущенный процесс продолжает ссылаться
на старый бандл (404 в браузере).

Действия после изменения CSS в RCL:
1. Пересобрать consuming-проект (`dotnet build`).
2. Перезапустить приложение (kill + запуск заново).
3. Обновить страницу в браузере (Ctrl/Cmd+R).

### Blazor: Razor-параметры — `@` для C#-выражений (КРИТИЧНО)

- В Razor-шаблонах параметр компонента `Prop="value"` передаёт **литеральную строку**.
- Для передачи значения C#-поля/выражения обязательна `@`-инфиксация: `Prop="@field"`.
- Без `@` компонент получает литерал, а не значение — ошибка невидима на этапе компиляции.
- Пример: `Token="_jwtToken"` → передаёт строку `"_jwtToken"`, `Token="@_jwtToken"` → значение поля.

### Blazor Server: `HttpClient` loopback без cookie (КРИТИЧНО)

- `HttpClient` в Blazor Server выполняет **server-to-server** запросы (loopback). Браузерные cookie **не передаются**.
- JWT-middleware по умолчанию читает токен только из cookie (`OnMessageReceived`).
- Для loopback-запросов JWT передаётся через `Authorization: Bearer` заголовок.
- JWT-middleware **обязан** проверять оба источника: сначала `Authorization` header, затем cookie.
- Паттерн: читать JWT из cookie в `OnInitializedAsync` (когда HTTP-контекст доступен), передавать как параметр компоненту.

### Blazor: `InputFile` stream — копировать в память до async-операций (КРИТИЧНО)

- `IBrowserFile.OpenReadStream()` ссылается на **браузерный** файл через Blazor Circuit.
- При `StateHasChanged()` (ре-рендер) reference на поток **теряется** → `_blazorFilesById` null.
- Обязательно: копировать данные через `Task.Run` (чтение на thread pool) **ДО** первого
  `StateHasChanged()` — ре-рендер чистит `_blazorFilesById` на клиенте до завершения чтения.
- Синхронное чтение (`browserStream.Read()`) невозможно — `OpenReadStream` не поддерживает.
- Шаблон:
  ```csharp
  using var ms = new MemoryStream();
  await Task.Run(async () => {
      using var bs = file.OpenReadStream(maxSize);
      await bs.CopyToAsync(ms).ConfigureAwait(false);
  });
  ms.Position = 0;
  // ... теперь безопасно вызывать StateHasChanged()
  ```

### Правило: отображение загруженного файла через FileUpload (КРИТИЧНО)

При использовании компонента `FileUpload` для загрузки **одного файла** (не в список) загруженный файл отображается **как кнопка-ссылка**, а не в отдельном блоке под полем загрузки.

- После успешной загрузки: `FileUpload` скрывается, вместо него — кнопка «📄 имя_файла» + кнопка «Заменить».
- Кнопка «Заменить» показывает `FileUpload` повторно.
- Имя файла берётся из ответа API (`OriginalName`) через колбэк `OnFileUploadedInfo`, а не хардкодится.
- **Исключение**: правило не действует при загрузке нескольких файлов в список (множественная загрузка).

### Ошибки HTTP — показывать тело ответа (КРИТИЧНО)

- `EnsureSuccessStatusCode()` выбрасывает `HttpRequestException` **без тела ответа** — сообщение сервера скрыто.
- При обработке ответов API: **всегда читать тело** перед выбросом исключения при не-2xx статусе.
- Шаблон:
  ```csharp
  if (!response.IsSuccessStatusCode)
  {
      var body = await response.Content.ReadAsStringAsync();
      throw new HttpRequestException($"HTTP {(int)response.StatusCode}: {body}");
  }
  ```
- Правило действует для всех HTTP-клиентов: `FileUpload`, внешние API-клиенты, интеграции.

### EF Core: `HasDefaultValue` для enum — через значение enum, не через `int`

- `HasDefaultValue(0)` для enum-свойства падает на этапе design-time с ошибкой
  «Cannot set default value '0' of type 'int' on property of type 'Enum'».
- Правильно: `HasDefaultValue(DocumentFlowType.Paper)` — передавать значение
  самого enum, а не числовой литерал.

### Схема БД: проверять соответствие EF-маппинга реальной структуре таблиц

- При изменении EF-маппинга (или при первом обращении к таблице) сверять:
  имя таблицы (`ToTable`), первичный ключ (`HasKey`), имена колонок (`HasColumnName`),
  имена индексов — с реальной структурой в БД (`\d table_name`).
- Несовпадение приводит к ошибкам `42P01: relation does not exist` или неверной
  работе связей.
- Пример: `OkopfConfiguration` была на таблицу `okopf` с PK по `Code`,
  а в БД таблица `ref_okopf` с PK `Id`.

### Валидация: зеркалирование клиент-сервер (КРИТИЧНО)

- Клиентская валидация (`IsStepValid` / `AreXxxFieldsValid`) обязана
  проверять **все** условия, которые проверяет серверная (`SaveEdit`).
  Частичная проверка приводит к тому, что вкладка остаётся зелёной,
  а `stepReachable` не ломается — ошибка обнаруживается только при
  финализации.
- Пример: `IsProtocolStepValid()` проверяет не только «подписан + дата есть»,
  но и «дата в допустимом диапазоне».

### Валидация: разделение form-валидатора и DB-валидатора (КРИТИЧНО)

- **Form-валидатор** (поля объекта) — проверяет значения полей текущей формы:
  диапазоны, обязательность, совместимость. Не обращается к БД.
  Пример: `OsaMeetingValidator` — проверяет `ShareholdersCount`, `GosaYear`,
  конфликт «заочное + интервал ГОСА».
- **DB-валидатор** (уникальность по БД) — проверяет бизнес-правила, требующие
  выборки из БД: уникальность записей, существование связанных сущностей.
  Пример: проверка «не более 1 ГОСА в году» через `AnyAsync(...)`.
- Эти два типа валидации реализуются в **разных классах**.
- В unit-тестах form-валидатор и DB-валидатор тестируются в **разных файлах**:
  `*ValidatorTests.cs` (чистые тесты полей) и `*BusinessRulesTests.cs`
  (тесты с `FakeDbContext`).
- Для mock-объекта БД (`FakeDbContext`) **рекомендуется отдельный тестовый проект**
  (например, `Tests.Unit.Db`), чтобы явно отделить инфраструктурные тесты от
  тестов доменной логики.

### Сохранение: мягкое vs жёсткое

- «Сохранить» (промежуточное) — сохраняет без валидации, не блокирует.
- «Завершить» (финализация) — полная валидация, блокирует при ошибках.
- `QuickSave` вызывается при любом переходе между вкладками — данные
  не должны теряться при навигации по wizard.

### Данные формы: не дублировать и не изобретать поля

- Прежде чем добавлять новое поле в сущность/БД — проверить, не решает ли
  задачу уже существующее поле.
- Пример: для «даты проведения заседания» использовать существующий
  `GosaWindowStart`, а не добавлять `MeetingDate`.

### Список и счётчик: пересчитывать при каждом входе на вкладку

- При переходе на вкладку с таблицей, размер которой зависит от другого поля
  (например, `editBoardMemberNumber`), необходимо **пересчитывать количество
  строк**, а не только загружать из БД. БД может содержать устаревшее количество.
- Метод `EnsureBoardMemberCount()` добавляет/убирает строки до совпадения
  с заявленным количеством.

### Формы чтения/редактирования родительских сущностей — отдельный маршрут (КРИТИЧНО)

- Каждая карточка чтения/редактирования родительской сущности (ОСА, юридическое
  лицо, заседание СД, пользователь и т.п.) должна иметь **собственный URL**
  с идентификатором — `/{entity}/{id}` или `/{entity}/{id}/edit`.
- Запрещено переключаться между списком и карточкой редактирования через флаги
  (`isEditing`, `editingId`) на одной странице. Это приводит к:
  - потере состояния при навигации браузера (Back/Forward);
  - невозможности прямого перехода по ссылке на конкретную запись;
  - раздуванию кодовой базы страницы (god-page) со смешанной логикой списка
    и редактирования.
- Исключение: wizard-формы с внутренним степпером (например, ОСА с вкладками
  «Параметры → Проведение → ... → Финализация»), где навигация по шагам —
  часть неделимого бизнес-процесса. Но переход между списком ОСА и карточкой
  конкретного ОСА — через отдельные маршруты `/admin/osa` и `/admin/osa/{id}`.

### Mermaid: круглые скобки в метках узлов требуют кавычек

- В Mermaid-диаграммах круглая скобка `(`/`)` в тексте метки узла
  (внутри `[...]`, `{...}`, `(...)`) вызывает ошибку парсинга, если
  метка не обёрнута в двойные кавычки.
- Правильно: `C4["Дата поступления (если задано)"]` — вся метка в `"..."`.
- Неправильно: `C4[Дата поступления (если задано)]` — `(` внутри `[` без кавычек.
- Правило действует для всех форм узлов Mermaid: прямоугольных `[...]`,
  ромбовидных `{...}`, скруглённых `(...)` и других.

### E2E-тесты: игнорировать HTTP-статус при проверке SPA контента (КРИТИЧНО)

Playwright `page.Response` возвращает результат первой загрузки страницы (HTML-document). Для интерактивных страниц Admin Console, где доступ защищён `[Authorize]`, страница может загрузиться со статусом 200 — содержимое будет либо полноценным контролом, либо базовой Blazor-оболочкой с `<div id="blazor-error-ui"> ... An unhandled exception has occurred ... </div>`. Проверять HTTP-статус по факту бессмысленно — он всегда 200. Вместо этого нужно сравнивать текст видимого контейнера `.content` или наличие специфичного контента (кнопки, таблицы, формы), что напрямую отражает правильность рендеринга.

Антипаттерн:
```csharp
// ❌ Статус почти всегда 200 — бесполезная проверка
page.Response.StatusCode.Should().Be(200);
```

Паттерн:
```csharp
// ✅ Рендерен ли нужный контент? (кнопка, таблица, ссылка)
(await page.QuerySelectorAsync("button.btn-primary:has-text('Создать уведомление')"))
    .Should().NotBeNull();
// Если контрол не рендерится — тест падает. Если блейз падает — тоже падает.
```

### E2E-тесты: Playwright `IPage` не Disposable (КРИТИЧНО)

Playwright `IPage` **не реализует** ни `IDisposable`, ни `IAsyncDisposable` (до версии 1.50 включительно). Использование `using var` / `using (...)` для переменной типа `IPage` вызывает ошибку компиляции CS8410 (CS1674).

Правильно:
```csharp
// Обычная переменная — сборщик мусора освободит ресурсы при выходе из теста
var page = await _browser.NewPageAsync(new BrowserNewPageOptions { IgnoreHTTPSErrors = true });
```

Неправильно:
```csharp
// ОШИБКА CS8410 / CS1674
using var page = await _browser.NewPageAsync();
```

### E2E-тесты: централизованная конфигурация URLs (КРИТИЧНО)

Зафиксирован инцидент: адреса серверов (`http://localhost:5002`, `http://localhost:5001`)
были захардкожены магическими строками в каждом E2E-тесте. При изменении портов пришлось
править все файлы вручную.

Правило: все адреса сервисов, используемых в тестировании, хранятся в одном месте.

Шаблон реализации:
1. Определите enum:
   ```csharp
   public enum Portal { BoardPortal, AdminConsole }
   ```
2. Храните базовые URI статически (или в конфиге):
   ```csharp
   public static class PortalUrls {
       public const string BoardPortal = "http://localhost:5002";
       public const string AdminConsole = "http://localhost:5001";
   }
   ```
3. Предоставьте helper-методы вместо строковых URL напрямую:
   ```csharp
   // Вместо: CreatePageAsync("http://localhost:5002/meetings")
   // Используйте: fixture.CreateBoardPortalPageAsync("/meetings");
   ```
4. Файл `appsettings.test.json` в проекте функциональных тестов позволяет менять
   значения без перекомпиляции через `IConfiguration`.

Это правило действует также для любых внешних сервисов в тестах: SMTP, БД, Redis, S3.

### Структура тестов

```csharp
[Fact]
public async Task CreateAsync_WhenValidRequest_ShouldReturnNewId()
{
    // Arrange
    var request = new CreateMeetingRequest
    {
        MeetingForm = MeetingForm.InPerson,
        VotingEndAt = DateTime.UtcNow.AddDays(1)
    };

    _repositoryMock
        .Setup(x => x.AddAsync(It.IsAny<Meeting>(), It.IsAny<CancellationToken>()))
        .ReturnsAsync(new Meeting { Id = 1 });

    // Act
    var result = await _sut.CreateAsync(request);

    // Assert
    result.Should().BeGreaterThan(0);
}
```

### Фреймворки

- **xUnit**: Тестовый фреймворк
- **Moq**: Мокинг
- **FluentAssertion**: Утверждения

### DB-валидаторы: тестирование через Moq (КРИТИЧНО)

- DB-валидаторы (проверки, требующие выборки из БД: уникальность,
  существование связанных сущностей) должны принимать абстракцию
  `IApplicationDbContext` (порт из Domain), а не конкретную коллекцию
  или EF-контекст. Это Dependency Inversion: ядро не знает о EF Core.
- В unit-тестах используется **Moq** для мока `IApplicationDbContext`
  и его свойств (например, `Mock<DbSet<OsaMeeting>>` через
  `.Setup(db => db.OsaMeetings).Returns(mockSet.Object)`).
- Запрещено передавать в DB-валидатор конкретные коллекции
  (`List<T>`, `IEnumerable<T>`) — выборка из БД должна происходить
  внутри валидатора через `IApplicationDbContext`, чтобы тест проверял
  реальную логику, а не «предварительно отфильтрованные» данные.
- Шаблон теста:
  1. Arrange: создаётся `Mock<IApplicationDbContext>`, настраивается
     `Mock<DbSet<T>>` с тестовым списком и провайдером `IQueryable`.
  2. Act: вызывается метод валидатора с mock-объектом.
  3. Assert: проверяется результат (ошибки/успех) через FluentAssertions.

## Безопасность

### Проверка компонентов на уязвимости (CVE)

- При добавлении нового пакета/компонента проверять его на известные
  уязвимости (CVE) через GitHub Security Advisories, Snyk, NVD.
- Результат проверки заносить в `docs/security/vulnerability-check.md`.
- Рекомендовать компоненты с наименьшим количеством уязвимостей в истории;
  при равных показателях — с более активным циклом исправлений.
- При добавлении компонента сообщать пользователю о наличии известных
  уязвимостей (если есть — с оценкой критичности и рекомендацией).

### Чувственные данные

- Не коммитьте секреты в репозиторий
- Используйте `.env` для локальных настроек
- Шифруйте PII данные на уровне приложения

### Аутентификация

- OAuth2 + 2FA для ПК
- JWT Bearer tokens
- ПЭП (СМС) для голосования
- УКЭП (КриптоПро) для председателей

## Git Flow

| Ветка | Назначение | Защита |
|-------|------------|--------|
| `main` | Продакшн | 2 reviewers + CI |
| `develop` | Интеграция | 1 reviewer + CI |
| `feature/*` | Фичи | PR → develop |
| `bugfix/*` | Исправления | PR → develop |
| `hotfix/*` | Экстренные | PR → main + develop |

### Правило: первый коммит

Первый коммит в репозитории всегда имеет название `Initial commit`, независимо от
содержимого. Никаких `feat: ...`, `chore: initial scaffold` и т.п. — только
`Initial commit`.

### Правило: коммиты только по запросу пользователя (КРИТИЧНО)

Запрещено выполнять `git commit` без **явного** запроса от пользователя
(«закоммить», «коммитни», «сделай коммит», «push» и т.п.).
Коммит всегда сопровождается `git push` в том же ответе.

- Если пользователь не просил коммить — файлы остаются в working tree.
- При push возникает конфликт — вопрос выносится пользователю.

### Commit Message

```
<type>(<scope>): <description>

feat(meeting): add automatic quorum calculation
fix(voting): correct vote counting logic
docs(api): update voting endpoints
```
