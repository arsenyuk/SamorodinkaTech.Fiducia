### BDR-021: Единая таблица нотариальных заверений

Статус: Принято
Дата: 2026-08-19

Контекст:
Нотариальные заверения сопровождают множество бизнес-процессов: сделки с долями, оферты, заявления о выходе. Каждый тип документа может потребовать нотариального заверения. Без общей модели каждая сущность создавала бы собственную таблицу нотариальных заверений, что приводило бы к дублированию схемы.

Решение:
Создать единую таблицу `notarization` для всех нотариальных действий в системе. Каждый тип нотариального действия — одна запись с полем-дискриминатором `document_type`. Таблица хранит скан документа (`document_file_id` → `files`) и атрибуты заверения (ФИО нотариуса, реестровый номер и т.д.).

**Структура таблицы:**
```sql
CREATE TABLE notarization (
    id uuid PRIMARY KEY,
    legal_entity_id uuid NOT NULL,
    document_type varchar(50) NOT NULL,       -- SHARE_OFFER / EXIT_APPLICATION / OTHER
    related_entity_id uuid,                   -- ID связанной сущности
    related_entity_type varchar(50),          -- share_request / и т.д.
    document_file_id uuid NOT NULL,           -- FK → files (скан документа)
    notary_full_name varchar(300) NOT NULL,   -- ФИО нотариуса
    notary_license_number varchar(100),       -- Номер лицензии
    registry_number varchar(100),             -- Реестровый номер в ЕИС
    notarization_date date NOT NULL,          -- Дата заверения
    valid_from date,                          -- Действует с
    valid_until date,                         -- Действует до (NULL = бессрочно)
    created_at timestamp with time zone,
    created_by uuid
);
```

**Схема связей:**
```
files ←── notarization ←── share_request (notarization_id)
                              ↑
                              │ (может ссылаться)
board_participant_change, meeting, ...
```

Последствия:
- Позитив: единый паттерн для любых нотариальных заверений; нет дублирования схемы; расширяемость (новый тип документа не требует новой таблицы)
- Негатив: потеря типобезопасности (одна таблица для разных типов документов); необходимость проверки `document_type` на уровне приложения

Правила:
- `document_type` обязателен и должен соответствовать перечню допустимых значений
- `document_file_id` обязателен — каждое нотариальное заверение должно иметь скан документа
- При добавлении нового типа нотариального документа — добавить значение в `document_type`
- Отзыв нотариальной оферты требует нотариального заверения отзыва
