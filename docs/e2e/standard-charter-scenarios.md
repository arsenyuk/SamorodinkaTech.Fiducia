# Сквозные E2E-сценарии для 36 типовых уставов ООО

## Назначение

Документ описывает 36 сквозных (end-to-end) сценариев тестирования, покрывающих все типовые уставы ООО, утверждённые Приказом Минэкономразвития России от 01.08.2018 № 411.

Каждый сценарий проверяет полный жизненный цикл настройки юридического лица: от сброса базы данных до сохранения ЮЛ с выбранным типовым уставом.

---

## Предусловия

- Запущена инфраструктура: PostgreSQL, OpenLDAP, phpLDAPadmin, MinIO
- Запущены приложения: Admin Console (порт 5001), Board Portal (порт 5002)
- Auth:Method = "Basic" (для тестов)
- Playwright браузер установлен (`dotnet tool install Microsoft.Playwright` + `pwsh bin/Debug/net9.0/playwright.ps1 install`)

---

## Общая структура сценария

Каждый из 36 сценариев (устав №01 — №36) выполняет следующие шаги:

### Шаг 0: Сброс БД и сидирование данных (ОДИН раз)

**Действие:** Перед прогоном всех тестов выполняется однократный сброс БД и создание всех ЮЛ + LDAP-пользователей.

**Порядок:**
1. Сброс БД (`--no-demo`)
2. Удаление старых LDAP-пользователей
3. Создание LDAP-пользователей для всех 50 ЮЛ (36 типовых + 14 нетиповых)
4. Логин SYS_ADMIN в Admin Console
5. Создание всех 50 ЮЛ типа ООО
6. Назначение ролей (LE_ADMIN + CEO) для ЕИО каждого ЮЛ

**Фиксированный набор данных:** `CharterTestDataFixed.cs` содержит:
- 50 юридических лиц (36 типовых + 14 нетиповых уставов)
- Для каждого ЮЛ: набор лиц (ГД + участники) с фиксированными ФИО и долями

### Шаг 1: Логин ГД в Board Portal

**Действие:** Открыть Board Portal, войти как ГД конкретного ЮЛ.

**Данные для входа:** Берутся из `CharterTestDataFixed.PersonsByEntity[номер]`:
- Для ExecutiveBody A: `persons.Gd.FullName`
- Для ExecutiveBody B/C: `persons.Participants[0].FullName`

**Ожидаемый результат:** Редирект на `/main`.

### Шаг 2: Заполнение полей ЮЛ + выбор устава + сохранение

**Действие:** Перейти на `/legal-entities`, заполнить поля и выбрать устав.

#### Вкладка "Карточка ЮЛ" (таб 0):

| Поле | Значение |
|------|----------|
| Краткое наименование | Из `CharterTestDataFixed.LegalEntities[n].ShortName` |
| ОГРН | Из `CharterTestDataFixed.LegalEntities[n].Ogrn` |

#### Вкладка "Устав" (таб 3):

| Поле | Значение |
|------|----------|
| Номер типового устава | 01–36 (соответствует номеру ЮЛ) |

**Ожидаемый результат:** Устав успешно выбран. Сохранение без ошибок.

### Шаг 3: Добавление участников (опционально)

**Действие:** Добавить участников через API `POST /api/participants`.

**Условие:** Шаг выполняется **только** для уставов с ExecutiveBody A (№01–06, №19–24).
Для уставов с ExecutiveBody B (№07–12, №25–30) и C (№13–18, №31–36) шаг **пропускается**.

**Данные участников:** Берутся из `CharterTestDataFixed.PersonsByEntity[номер].Participants`:

| Поле | Формат |
|------|--------|
| participantType | FL |
| fullName | Из фиксированных данных |
| sharePercent | Из фиксированных данных |

**Ожидаемый результат:**
- API возвращает JSON с `Id` созданного участника
- GET `/api/participants` возвращает массив с количеством участников из фиксированных данных
- Отсутствуют ошибки

### Шаг 4: Проверка записей аудита

**Действие:** Проверить, что все операции залогированы в файле аудита (`audit-{yyyyMMddHH}.log`).

**Проверяемые события:**

| Событие | actionCode | Описание |
|---------|------------|----------|
| Вход в систему | `LOGIN_SUCCESS` | Логин пользователя из фиксированных данных |
| Сохранение данных ЮЛ | `DATA:UPDATE` | PUT-запрос к `/api/legal-entities` |
| Добавление участников | `DATA:CREATE` | POST-запрос к `/api/participants` (только для типа A) |
| Отсутствие ошибок доступа | — | Нет записей `ACCESS:PAGE_DENIED` |

**Формат строки аудита:**
```
[{timestamp}] [AUDIT] {actionCode} | User={login} IP={ip} | {description} | {entityName} {entityId}
```

**Хелпер для проверки:** `AuditLogHelper.cs` — читает файл аудита и ищет записи по actionCode, логину или тексту.

**Ожидаемый результат:**
- Запись `LOGIN_SUCCESS` с логином ГД
- Запись `DATA:UPDATE` для операции сохранения ЮЛ
- Запись `DATA:CREATE` для операции добавления участников (если применимо)
- Отсутствие записей `ACCESS:PAGE_DENIED`

### Шаг 5: Проверка ошибок в логе приложения

**Действие:** Проверить отсутствие ошибок (ERROR/FATAL) в логе приложения (`app-{yyyyMMddHH}.log`) за период работы теста.

**Привязка к тесту:**
- Фиксируется `testStartTime` (время начала теста)
- Фиксируется `testEndTime` (время окончания теста)
- Читаются только записи за период `[testStartTime, testEndTime]`
- Имя теста передаётся в сообщение об ошибке для идентификации

**Запрет параллельного исполнения:**
- Оба класса тестов (`E2E_StandardCharterTests`, `E2E_NonStandardCharterTests`) имеют атрибут `[Collection("CharterTests")]`
- xUnit выполняет тесты из одной коллекции последовательно, что гарантирует отсутствие пересечения логов

**Формат строки лога:**
```
{Timestamp:yyyy-MM-dd HH:mm:ss.fff zzz} [{Level:u3}] {SourceContext} | {Message:lj}
```

**Хелпер для проверки:** `AppLogHelper.cs` — читает файл лога, фильтрует по времени, ищет записи уровня ERR/FTL.

**Ожидаемый результат:**
- Отсутствие записей уровня `ERR` или `FTL` за период работы теста
- Если ошибки найдены — сообщение содержит имя теста, временной диапазон и детали ошибок

## Запуск тестов

### Все 36 тестов:

```bash
dotnet test tests/SamorodinkaTech.Fiducia.Tests.Functional/ \
  --filter "E2E_StandardCharterTests" \
  --logger "console;verbosity=detailed"
```

### Один конкретный устав (например, №01):

```bash
dotnet test tests/SamorodinkaTech.Fiducia.Tests.Functional/ \
  --filter "StandardCharter_CompleteFlow=1" \
  --logger "console;verbosity=detailed"
```

### Несколько уставов:

```bash
dotnet test tests/SamorodinkaTech.Fiducia.Tests.Functional/ \
  --filter "StandardCharter_CompleteFlow=1|StandardCharter_CompleteFlow=2|StandardCharter_CompleteFlow=3"
```

## Требования к среде

| Компонент | Минимальная версия | Порт |
|-----------|-------------------|------|
| .NET SDK | 9.0 | — |
| PostgreSQL | 16 | 5434 |
| OpenLDAP (bitnami) | 2.6 | 389 |
| phpLDAPadmin | latest | 8082 |
| Admin Console | net9.0 | 5001 |
| Board Portal | net9.0 | 5002 |
| Playwright | 1.52.0 | — |

### Быстрый старт инфраструктуры:

```bash
# Запустить PostgreSQL
docker-compose up -d postgres

# Запустить OpenLDAP + phpLDAPadmin
docker-compose -f docker-compose.ldap.yml up -d

# Загрузить seed-данные в LDAP
docker exec -i openldap ldapadd -x -D "cn=admin,dc=bryansk-arsenal,dc=local" -w ldappassword < tools/ldap/seed-bitnami.ldif

# Запустить приложения
dotnet run --project SamorodinkaTech.Fiducia.AdminConsole &
dotnet run --project SamorodinkaTech.Fiducia.BoardPortal &

# Установить Playwright браузер
pwsh tests/SamorodinkaTech.Fiducia.Tests.Functional/bin/Debug/net9.0/playwright.ps1 install
```

## Возможные проблемы и решения

| Проблема | Решение |
|----------|---------|
| phpLDAPadmin недоступен | Убедиться, что `docker-compose -f docker-compose.ldap.yml up -d` выполнен |
| DbReset не находит `tools/db` | Установить переменную `FIDUCIA_REPO` или запускать из корня репозитория |
| Браузер Playwright не установлен | `pwsh playwright.ps1 install` в директории с тестами |
| Тест завис на登录 | Проверить, что Auth:Method = "Basic" в `appsettings.json` обоих порталов |
| Нет опции "Васильева" в dropdown | Выполнить шаг 1 (сброс БД) — она создаётся в seed-данных |
| Нет опции "Тестов" в Board Portal dropdown | Пользователь должен быть создан в шаге 2 и добавлен в шаге 6-7 |
